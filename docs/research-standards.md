# Research standards

These rules exist because the main failure of AI-conducted research is a
confident, well-written claim that is wrong. Every rule below is a way of
making a claim cheap for someone else to check.

## Evidence labels

Every claim in a project's Claims table carries exactly one label. The
project's front-matter `evidence` field is the label of its **weakest headline
claim**.

| Label | Meaning | What a reader does to check |
|---|---|---|
| `proved-formal` | Machine-checked proof, in [rabidlorax/math](https://github.com/rabidlorax/math) and cited from the project by name, commit, axioms and permalink (see below) | Build the math repository at the pinned commit; read the theorem statement to confirm it says what is claimed |
| `proved-informal` | Complete written proof, every step explicit, not yet formalized. A temporary label | Read the proof |
| `computed` | Output of code in the repository, regenerated by the documented command, depending on no external data | Run the command |
| `external-data` | Follows from analysis of data or published results that we did not produce and cannot reproduce | Run the analysis; trust in the source is separate and stated |
| `literature` | Reported by a cited source; not re-derived here | Read the source |
| `conjecture` | Supported by argument or numerical evidence, not established | Nothing to check yet; the project says what would settle it |

Rules:

- Numerical evidence never upgrades a mathematical claim past `conjecture`.
- A proof that depends on a computation is only as strong as the computation;
  list both.
- A formal proof proves the formal statement. Say in words how the formal
  statement relates to the informal one.
- `proved-informal` is not a resting state. Formalizing is cheap, so a written
  proof is expected to be formalized and the claim upgraded to
  `proved-formal`. If formalization is impractical (the foundations are
  missing from Mathlib, for example), say so in the project's limitations.
- Predictions about the physical world (a candidate planet, a material, a
  biological mechanism) are `conjecture` until someone with the right
  instrument checks. State what observation or experiment that is.

## Proofs live in the math repository

This repository holds no Lean code. Every proof, including a proof that only
serves a project in another domain, goes in
[rabidlorax/math](https://github.com/rabidlorax/math), and the project here
cites it. That keeps one place where all proofs are built and audited.

### Where a proof goes there

- A proof specific to one project here goes in that repository's `MathApplied`
  library, at `MathApplied/<Domain>/<Project>/<Topic>.lean`, where `<Domain>`
  and `<Project>` are the CamelCase forms of this repository's domain and
  project slug. `domains/physics/projects/ising-small-lattices` becomes
  `MathApplied/Physics/IsingSmallLattices/`.
- A result that turns out to be general goes in its `MathInfra` library.
- Follow that repository's own rules (`README.md` and `CLAUDE.md` there),
  including its prior-art check, the plain-language `-proofs.md` file beside
  each Lean file, and the `Axioms` test file.

### How to cite a theorem

A `proved-formal` claim cites its theorem with four things:

- the **Lean declaration name**, exactly as it appears in the topic's `Axioms`
  test file. Declarations there are in the root namespace, so the name has no
  library or path prefix
- the **commit hash** of the math repository at which it was checked: a commit
  on its `main` branch at which `lake build` passes with no warnings
- the **axioms** it depends on, copied from the topic's `Axioms` test file at
  that commit. Anything beyond `propext`, `Classical.choice` and `Quot.sound`
  is justified in the project. An axiom with `native_decide` in its name (or
  `Lean.ofReduceBool`) means the proof trusts the Lean compiler as well as the
  kernel; say so
- a **permalink** to the theorem's statement at that same commit:
  `https://github.com/rabidlorax/math/blob/<full commit hash>/<path>#L<line>`

The permalink must use the full 40-character commit hash, and the same commit
as the citation. Never link to a branch (`blob/main/...`): topics there move
between folders, so a branch link breaks or silently points at something else.
A permalink stays valid after a move. `scripts/check_repo.py` rejects links
into the math repository that are not pinned to a full commit hash.

The name, commit and axioms identify the theorem. The permalink is how a
reader gets to it in one click. Example of the format:

> [`lucasU_eq_zero_iff_lucasRank_dvd`](https://github.com/rabidlorax/math/blob/61234ace57586a0831c74996cd230bb8bd6b5484/MathInfra/New/LucasRank.lean#L125),
> rabidlorax/math at `61234ace57586a0831c74996cd230bb8bd6b5484`, axioms:
> `propext`, `Classical.choice`, `Quot.sound`.

To check a citation, check out that commit of the math repository, run
`lake build`, and read the theorem's statement to confirm it says what the
project claims.

The math repository checks this repository for a declaration's name before
renaming or deleting it. If a cited theorem does change, update the citation
here to the new name, commit and permalink.

### Conditional results, conjectures, computations

- A theorem proved **assuming a conjecture** takes the conjecture as an
  explicit hypothesis. The axiom audit does not show that dependence. A claim
  citing such a theorem says it is conditional and names the conjecture.
- A **conjecture** is stated in the math repository as a definition of a
  proposition (`def fooConjecture : Prop`). It is not a proof and cannot be
  cited as one; the claim here stays `conjecture`. It may still be linked by
  permalink so readers can see the exact statement.
- A **computation done outside Lean** is `proved-formal` only for the part
  where Lean checks a certificate. Say exactly what Lean verified and what is
  trusted. With no certificate checked in Lean, the claim is `computed`.

### Vocabulary and one exception

Everything proved in the math repository is `proved-formal` here. Its `New/`
folder corresponds to novelty `searched-none-found`, and
`FormalizedElsewhere/` to `partially-known` or `known`.

Verification artifacts tied to a specific program (a Dafny proof, a TLA+
specification, a model-checker run) stay in the project next to the code they
verify, with the tool and version recorded.

## The external-data disclaimer

Using existing research data is encouraged. Each project that does so must, in
its "External data and what we could not reproduce" section:

1. Name each source with version, DOI or URL, access date, and licence.
2. State that the underlying measurements were not made here and cannot be
   independently reproduced here.
3. Say which claims depend on that source, so a reader knows what falls if the
   source is wrong.
4. Note known problems with the source (biases, later corrections,
   retractions) that were found.

Commit the script that fetches the data and a checksum, not large raw files.
Respect licences and access terms. No personal or individual-level sensitive
data in the repository.

## Status lifecycle

| Status | Meaning |
|---|---|
| `proposed` | Question written down; little or no work done |
| `active` | Work in progress |
| `result` | A claim is made and documented; not independently reviewed |
| `verified` | A review independent of the original work is recorded in the review log and found no errors that change the headline claim |
| `refuted` | The hypothesis was shown false, or an earlier claimed result was found wrong. The write-up says which and why |
| `inconclusive` | Work finished without settling the question |
| `abandoned` | Stopped; the README says why and what was learned |

Independent review means a fresh session that did not see the original
reasoning, or a human. A model re-reading its own work in the same context is
not a review. Reviewers try to break the result: rerun the code, re-derive key
steps, look for the prior work the author missed.

`refuted`, `inconclusive`, and `abandoned` projects stay in the repository.

## Novelty

The front-matter `novelty` field takes one of:

- `unchecked`: no documented search (the default)
- `searched-none-found`: a search is documented in the project and found no
  prior statement of the result
- `partially-known`: related results exist; the project says what is new
- `known`: an independent rederivation, exposition, formalization, or
  replication of an existing result

Do the search before the work, not after, and report what it finds before
investing in the project. A documented search:

- covers the places a result of this kind would appear (for a formal proof:
  Mathlib, open and closed Mathlib pull requests, other Lean projects, the
  Isabelle Archive of Formal Proofs, Rocq, HOL; for other work: the field's
  preprint server, databases, and reference catalogues)
- searches the **alternative names** the literature uses for the same object,
  and records them
- looks inside what it finds. A matching title does not show that the planned
  result is there, or that it is not
- is **dated**. Never write "not in X" without the version or date of X that
  was checked
- ends with one of: go ahead, narrow the scope to what is missing, or build on
  the existing work

If prior work turns up later, update the `novelty` field and the write-up.

Never write "novel", "first", or "new" without the search to back it, and
phrase it as "not found in the search described". Model memory of the
literature is incomplete and has a cutoff date; a claim of novelty from memory
alone is `unchecked`. Rediscovering a known result is fine and is labelled
`known`.

## Citations

- Cite only sources that were actually retrieved and read in the session, or
  mark the citation `[from memory, unverified]`.
- Never invent a reference, DOI, quotation, or page number. A missing citation
  is acceptable. A fabricated one is the most serious error possible here.
- Quote or point to the specific passage when a claim depends on it.

## Reproducibility

- One documented command regenerates each number and figure from a clean
  checkout.
- Pin dependency versions. Fix and record random seeds. Record runtime and
  hardware when they matter.
- Results that depend on a model's output (for example, an LLM used as a
  classifier) record the model ID, prompts, and raw outputs.

## Honest reporting

- Report what was tried, including what failed. If twenty searches were run
  and one hit, say twenty.
- State limitations specifically: what was not checked and what would change
  the conclusion.
- Use plain confidence language that matches the evidence label. No
  "groundbreaking", "revolutionary", or "solves".
- Record which models did the work in the front-matter `models` field, and any
  human contribution in the review log.

## What we will not do

Being "willing" is part of the selection of work. This repository does not
host:

- Work that gives meaningful uplift toward biological, chemical, nuclear, or
  radiological weapons, including pathogen enhancement and toxin design
- Offensive security tooling, undisclosed vulnerabilities, or evasion
  techniques
- Weapons design
- Analysis that identifies, profiles, or targets private individuals
- Individual medical, legal, or financial advice presented as such
- Claims of professional misconduct against named researchers (documented
  inconsistencies in papers are fine; see Metascience)

When a legitimate project comes near one of these lines, the project README
says where the line is and how the work stays on the right side of it.

## What we cannot do

State these limits rather than work around them silently:

- No new physical measurements of any kind
- Compute, memory, disk, and network are bounded by the session container
- Knowledge of the literature is incomplete and dated
- Models make arithmetic, citation, and reasoning errors while sounding
  certain; this is why everything above exists
